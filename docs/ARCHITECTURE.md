# pinax — アーキテクチャ設計書

## 1. 三本柱の中の pinax

自宅の 3 つのサービスは「相手には原理的に持てない情報」で切ってある。pinax はその 3 本目。

| | 持っている情報 | 持てない情報 |
|---|---|---|
| **DryEyes** | 前回スナップショット、既読位置、XPath、監視の文脈 | どのホスターなら落とせるか / もう持っているか |
| **PowerDowner** | ホスター実績表、エンジン振り分け、リトライ、保存先 | そのページで何が「新しい」のか |
| **pinax** | **手元の棚に何があるか**、欠番、完結、書誌と書影 | どこから落とすか / 何が新しく出たか |

```
DryEyes                     PowerDowner                    pinax
何が「新しい」のか      →    どう「落とす」のか       →    何を「持っている」のか
                             ← 「これ持ってる?」 ────────┘
```

**pinax は落とさないし、探さない。** 棚を見て答えるだけ。

## 2. なぜ pinax を立てるのか

今 PowerDowner が `items` 表 (取得済み台帳) を持っていて、DryEyes から投入が来ると
「もう持っているか」を自分で判定している。それには 2 つ無理がある。

1. **台帳はダウンロードの記録であって、棚の姿ではない。** 手で NAS に置いたもの、
   落とす前から持っていたもの、消したものが台帳に反映されない。
   PowerDowner の README にもある通り「間違った行が 1 つあるだけでその巻は永久に落ちてこない」
2. **蔵書そのものを見たい要求に応えられない。** 表紙を並べる、欠番を探す、手元へ落とす —
   これはダウンローダの仕事ではない

pinax は**ファイルそのものを正**にする。台帳を信じるのではなく、棚を毎回読む。

## 3. データの持ち方

```
series (作品)  ─┬─ volumes (巻)  ─── files (実ファイル)
                └─ covers / bib (外から取った書影と書誌)
```

### 作品の単位はフォルダ

`series` の一意キーは `(root_id, folder)`。**`series_key` ではない。**

蔵書は作品ごとにフォルダで分けてある。「同じフォルダに入っている = 同じ作品」は
人が既に下した判断で、ファイル名より強い。実物で確かめた通り、ファイル名を正にすると割れる:

```
[おがきちか] Landreaall/[おがきちか] Landreaall ランドリオール 第37巻.rar
  → 副題の有無で landreaall と landreaallランドリオール の 2 作品になる
```

一方 `series_key` (= `seriesKeyOf(title)`) は**同一性の判定にだけ使う別軸**で、一意ではない。
`[BETEMIUS] 同人誌` と `[河内和泉] 同人誌` は同じキーだが別の棚になる。

**この 2 つを 1 本にまとめてはいけない。** 用途が違う:

| | 使うところ | 一意か |
|---|---|---|
| `folder` | 棚としての作品。画面に並ぶ単位 | 根の中で一意 |
| `series_key` | 外から「作品名」だけで所持を聞かれた時の突き合わせ | 一意でない |

### 「持っている」と「出ている」を混ぜない

`holdings` と `published` は**別の軸**として持つ。

```
holdings  … ファイルを見て分かること。          事実
published … 外の書誌に聞いて分かること。        下限の推定
```

棚だけを見ていると「1〜10巻が揃っている」としか言えず、11巻以降が出ていることに
気付けない。かといって書誌を棚と同じ確からしさで扱うと、外が知らない巻を
「出ていない」と断定してしまう。**どちらも間違い方が買い逃しに直結する**ので、
`published.max` は「全 N 巻」ではなく「**少なくとも N 巻までは出ている**」と読む。

素は `bib` 表。enrichSeries は NDL の答えを**持っていない巻も含めて**書く
(表紙は持っている巻の分しか取りに行かない — 持っていない巻の表紙まで焼くと
「持っている」の意味が濁る)。

完結しているかは `src/published.ts` の頭に書いた通り、**外からは分からない**。
確かなのは人が下した判断だけで、それは 2 通りある:

```
series.completed        フォルダ名の (完)。**スキャンが書く列**
series.completed_user   画面で人が決めた値。null なら未指定
```

**同じ列にまとめてはいけない。** 人の指定をフォルダ由来の列へ書くと次のスキャンが
ファイルを見て上書きし直し、指定が黙って消える。逆に人の指定でフォルダ名を直しに行くと
「ファイルが正」という土台そのものが崩れる。読み出す時だけ `COALESCE(completed_user, completed)`
で 1 つの答えにして、**どちらが言ったか** (`completedBy`) も一緒に返す — 画面が
「完結（フォルダの (完)）」と「完結（この画面で指定）」を書き分けられるように。

画面に出すのはスイッチ 1 つ (`完結済み`) だけにしてある。列としては 3 状態
(未指定 / 完結 / 継続中) だが、**人に 3 択を見せる必要は無い** — 触るまではフォルダの
答えがそのまま入っていて、触れば人の指定になる、で説明が足りる。

### 人が下した判断は、機械が書く列と分けて持つ

完結 (`completed_user`) と同じ形の列がもう 2 つある。**どれも「機械が当てたもの」とは
別の場所に置き、自動の巡回が上書きしない。**

| 列 / 表 | 人が何を決めたか | 誰が書き換えないか |
|---|---|---|
| `series.completed_user` | 完結かどうか | スキャン |
| `series_pick` | **どの書誌シリーズが手元の棚か** | 自動の enrich |
| `covers.pinned` | この 1 巻の表紙はこの絵 | 自動の巡回、`refresh` 付きの取り直し |

`series_pick` が要るのは、**同じ作者が同じ書名で別のシリーズを並べている**から (5.6)。
`covers.pinned` はその下の粒度で、系列は合っているのに 1 巻だけ版が違う時の逃げ道。

**`refresh` は「外に聞き直す」であって「人の指定を捨てる」ではない。**
ここを混ぜると、選び直した表紙が取り直しのたびに元の取り違えへ戻る。

### 棚へ書き戻す道は 1 本だけ、人が押した時だけ

pinax は「棚を読んで DB を作る」一方向で立っている。そこに**フォルダ名の付け替え**
(`src/rename.ts`) という 1 本だけ書き戻す道を開けた。守る形はこう:

| | |
|---|---|
| 入口 | 人が画面で押した時だけ。**自動の巡回からは決して生やさない** |
| 段取り | 計画を返す → 人が見る → 押す。計画の段ではファイルに触らない |
| 排他 | `src/lock.ts`。スキャンと同時に走らせない |
| 記録 | `data/renames.jsonl` に 1 行ずつ。戻せる道を残す |
| 範囲 | フォルダ名だけ。**ファイル名と中身には触らない** |

**なぜ pinax の中でやるのか。** リネームの判断材料 (要確認・書誌・`series_pick`) は
全部 pinax の中にしかないので、三本柱の切り方 (「相手には原理的に持てない情報」) では
切る線が引けない。それ以上に実利があって、`series` の一意キーが `(root_id, folder)` である以上、
**外で名前を変えると次のスキャンが別の作品として新しい行を作る** — 焼いた表紙も
`series_pick` も `completed_user` も古い行に取り残され、棚からは消えたように見える。
DB を書けない道具にこれは直せない。

**完結の指定をフォルダへ書き出せるようになった。** `completed_user` はもともと
「フォルダを直せないから」作った逃げ道で、恒久的に持ちたい列ではない。フォルダ名に
`(完)` を書けば次のスキャンで `series.completed` が立つので、指定は外してよくなる
(`db.renameSeriesFolder` がその場で外す)。**「ファイルが正」を保ったまま人の判断が定着する。**

ただし `upsertSeries` は「一度立った完結は倒さない」ので、**印を外す向きの付け替えは
スキャン任せにできない**。`completed` はリネームの側でその場で書く。

### つじつまの合わないところは直さずに見せる

ファイル名から巻を読む以上、読み違えも読めないものも必ず残る:

```
本好きの下剋上 第04部 第01巻   部が違うのに全部「第01巻」に畳まれる
Landreaall 第01巻.rar と Landreaall ランドリオール 第01巻.zip   同じ巻が 2 本
巻数表現の無いファイル          何巻か読めない (files.volume_id が null)
```

**機械には正解が分からない。** 別版として両方置いているのか捨て漏れなのかは中身を見た人しか
決められないので、pinax は数えて並べるところまでをやり (`catalog.ts` の `SeriesIssues`)、
絞り込み (`issues=dup|loose|any`) とエクスプローラで人の手が届くようにする。

重複の数え方は**分割書庫の連番を落としたファイルの素**で見る (`foo.part1.rar` も `foo.r00` も
`foo`)。同じ巻に素が 2 つ以上あれば重複で、`.part2` / `.r01` は重複ではない —
ここを重複と言うと本物が埋もれる。SQL 側 (`fileBaseSql`) と JS 側 (`fileBaseOf`) で
同じ切り方をすること。片方だけ直すと、一覧では重複と出るのに開くと印が付いていない状態になる。

### 下ろせない警告は上げない — 外伝は読み違えではない

上の裏返し。**要確認に上げてよいのは、人が手を入れれば消えるものだけ**。消しようのないものを
上げ続けると、印そのものが「いつも付いているもの」になって読み飛ばされる。

巻数の無いファイルを全部「何巻か読めない」に数えていた結果がそれだった。手元では
**19 作品 / 607** が永久に要確認で、その中身は `鬼滅の刃 外伝` や `四月は君の嘘 Coda` —
巻数が付いていないのが正しいものだった (2026-09-18 実測)。

見分けは `naming.ts` の `sideLabelAfterFolder` が機械でやる:

| | 規則 | 結果 |
|---|---|---|
| 別巻 | フォルダ名を前置きとして剥がして残りがある | 残りが呼び名 (`外伝` / `Coda`) |
| 1 冊で完結 | 剥がした残りが空 | 呼び名は空文字 |
| 読めない | 前置きになっていない / 残りに数字がある | null — 要確認のまま |

単位の無い巻数を読む `bareVolumeAfterFolder` と**同じ根拠の裏返し**で、フォルダという文脈が
ある以上、作品名を除いた残りは巻数かその作品の中での呼び名しかありえない。

**数字の混じった残りは別巻にしない。** 別巻として読むことは要確認を下ろすことなので、
`c48-49` のような巻数の読み落としまで黙らせる方向に効く。歯止めは安全側 —
機械が黙るより、人に見せたまま残す方を採る。

結果は `files.side_label` に入る。**機械が毎回書き直す列**で、`completed_user` や
`covers.pinned` (人の判断) とは立場が違う。ファイル名に既に「外伝」と書いてあるものの
写しでしかないので、**人が維持する管理枠を足さなかった** — 足せばそれは「ファイルが正」の
土台を外した 37 行の別台帳になる。機械が読めない名前 (`[井上雄彦].zip`) の受け皿は、
列ではなく**ファイル名を直せるようにする**方 (§8.5)。

別巻は巻の数直線に乗せない。欠番にも最新巻にも効かせず、持っていることだけを言う。
要確認が下りたのは 19 件中 13 件で、残る 6 件は本当に人が見ないと決まらないものだけになった。

### 巻とファイルを分ける

1 巻に複数のファイルがぶら下がる。分割書庫 (`.part1` / `.r00`) と、同じ巻の別版 (`[LQ]`) の
両方があるため。`files.volume_id` が null なら「巻数を読めなかったファイル」で、
欠番の計算には参加しないが作品には属する。そのうち `files.side_label` が入っているものは
別巻 (上記)。**null と空文字を区別すること** — 空文字は「1 冊で完結している作品」、
null は「呼び名も読めなかった」で、要確認に上げるかどうかが変わる。

### 消えたものを消さない

スキャンで見なかったファイルは `present = 0` に倒すだけで行は残す。
**根が丸ごと読めない時はスキャン自体を中止する** — NAS が一時的に見えないだけの時に
蔵書がまるごと消えると、所持判定が「持っていない」に化けて全巻を落とし直すことになる。

## 4. PowerDowner との互換

**`seriesKeyOf` は PowerDowner の `src/volume.ts` と同一でなければならない。**

pinax の `src/volume.ts` はあちらからの移植で、足したのは完結マークの扱いだけ
(`stripCompletionMark`)。片方だけ直すと、向こうが「持っている」と言った巻を
こちらが「持っていない」と言い、静かに二重取得が始まる。

一方 `src/naming.ts` は**読み戻し専用**にしてある。組み立て (リネーム) 側は今は
PowerDowner にある。Z: の受け入れトレイを整理する段になったら、あちらの
`planName` / `fitPath` / `uniqueName` をここへ引き取る — 書く側と読む側が別々の規則を
持った瞬間に、自分で置いたファイルを自分で見つけられなくなる。

### 問い合わせの入り口では寛容にする

`/api/own` は DryEyes が送ってくる**抽出前の生テキスト**も受ける。
`[つくしあきひと] メイドインアビス 第03巻` の形で届くので、先頭の `[著者]` を
`parseFilename` で落としてからキーにする。落とさないと
`つくしあきひとメイドインアビス` になり、蔵書側の `メイドインアビス` と一生噛み合わない。

**落とす仕事は naming.ts に任せること。** 蔵書のファイル名を読むのと同じ関数を通すのが肝で、
`seriesKeyOf` そのものには手を入れていないので PowerDowner との互換は保たれる。

## 5. 外の世界との境目

**pinax から外へ出る問い合わせは `src/bib/cache.ts` の 1 本だけを通る。**
これがプロジェクトのテーマ ("Never burn. Remember Alexandria.") をそのまま形にした部分。

```
                        ┌──────────────────────────┐
  作品 ─▶ ndl.ts ──────▶│  cache.ts (唯一の窓口)   │──▶ 外部 API
                        │  ・生のまま焼き付ける      │
  他サービス ─▶ /api/bib/proxy ─▶│ ・期限切れでも捨てない │
                        │  ・提供元ごとに間引く      │
                        └──────────────────────────┘
                                    │
                            data/pinax.db (http_cache)
                            data/covers/  (焼いた書影)
```

- **期限切れのキャッシュを捨てない。** 外が落ちている時に古い値を返せることが値打ちで、
  「新しくないから何も返さない」が一番やってはいけない振る舞い。`stale` の印を付けて返す
- **書影はファイルとして焼く。** 名前は中身の SHA-256 なので、同じ画像は 1 つで済み、
  URL は永久に変わらない (`Cache-Control: immutable` を付けられる)
- **提供元を足すのはアダプタ 1 枚。** 楽天ブックス (`src/bib/rakuten.ts`)、
  openBD (`src/bib/openbd.ts`)、Google Books (`src/bib/google.ts`) は実際そうやって
  足した — `covers.ts` の `fetchCover` に 1 段挟むだけで、cache.ts の骨格は変えていない。
  足したのは**鍵を扱う相手のための 2 つの穴**だけで、これは提供元ごとの都合ではなく
  「鍵を持つ相手一般」に要るもの:
  - `cacheUrl` … 見出しに鍵を混ぜない。混ぜると DB に鍵が残り、鍵を替えた瞬間に
    焼いたキャッシュが全部迷子になる
  - `neverCacheStatuses` … 鍵や接続元 IP の間違いを焼かない。
    **「期限切れでも捨てない」は正しく取れた答えの話**であって、
    自分の設定ミスの記録を抱え込む口実ではない
- **「回しても無駄な失敗」は `ProviderStopError` で上げる** (`cache.ts`)。提供元ごとに
  名前を付けて継ぐ (`RakutenAuthError` / `GoogleAuthError` / `GoogleQuotaError`) が、
  **受け止める側は親だけを見る** — 提供元を足すたびに catch を書き足さずに済む。
  受けた側はその回を打ち切る。**回し続けると、取れるはずだった巻にまで
  「駄目だった」の印 (`bib.cover_tried_at`) だけが押されて進む**。
  ただし**文面は必ず分ける** — 鍵の間違いは人が直すもの、1 日の上限は明日になれば戻るもので、
  混ぜると正しい鍵を何度も見直させることになる

### 提供元の実力 (2026-09-15 実測)

| 提供元 | 書誌 | 書影 | キー登録 |
|---|---|---|---|
| **NDLサーチ** | 巻ごとの ISBN が取れる。著者を添えれば精度が高い | ISBN のうち約半分 | 不要 |
| **楽天ブックス** | 巻を漢数字で書く (「日常（十二）」) ので**巻の切り出しには向かない** | **ISBN 直引きで 3/4 前後。表紙の本命** | アプリ ID + アクセスキー + **接続元 IP の申告** |
| openBD | ISBN 起点でしか引けない | **200 件中 0 件。**版元ドットコム登録の本だけが持つ | 不要 |
| **Google Books** | ISBN 直引きは 94/100 当たる。書名は `intitle:"…"` で括れば精度が高い | ISBN 直引きは 14% だが、**書名で引くと電子版の書影が出る** | API キー (IP の申告は不要) |

**書誌は NDL、表紙は NDL → 楽天 → openBD → Google → (書名で) 楽天 → Google。**
得意なところだけ使う。楽天に書誌まで任せないのは、巻の区切りを漢数字から読み直す羽目に
なるからで、それは NDL が `dcndl:volume` で既に正しく持っている情報。

順番で効いているのは**提供元の並びより「ISBN で当たる道を先に全部試す」という段**の方。
ISBN で当たった絵は手元の本と同じ版だが、書名で拾い直した絵は刷り直した版や電子版でありうる。
だから `covers.provider` を `rakuten-title` / `google-title` と分けて残し、
後から「どこの絵か」を見分けられるようにしてある。

Google には**この相手だけの落とし穴が 2 つ**ある:

- **絵を持っていない巻にも 200 で「image not available」の灰色の板を返す。** 9KB〜82KB あるので
  大きさの足切りを素通りする。中身の SHA-256 で弾く (`GOOGLE_PLACEHOLDER_COVERS`)
- **大きい絵を持っているのは電子版として売っている記録だけ。** 書誌だけの記録は 128px の
  サムネイルしか持たない。`accessInfo` で見分けて、小さい絵は
  **他の道が全部駄目だった時の最後の 1 枚**に回す (楽天の 600px と並ぶと目に見えて粗いため)

楽天は 2026 年の刷新で口が丸ごと変わっている (旧ドメインは 2026-05-14 に停止):

```
https://openapi.rakuten.co.jp/services/api/BooksBook/Search/20170404
  ?applicationId=…&accessKey=…        ← 両方要る。片方だけでは通らない
```

**接続元のグローバル IP を申告した相手からしか通さない。** 回線の都合で IP が変わると
ある日を境に表紙が 1 枚も増えなくなるので、`npm run whoami` で今の IP を出せるようにし、
弾かれた時はログに理由を出す (`RakutenAuthError`)。黙って諦めさせない。
Google Books には IP の申告が無い代わりに**1 日の上限**があり、そちらは `GoogleQuotaError`。

## 5.5 画面を見ている相手と、pinax が動いている PC は別物

**`/api/series/:id/reveal` (エクスプローラで開く) だけは、効果が画面の外で起きる。**

pinax は Tailscale 越しにスマホからも開く。他の口は全部「聞かれたことに答える」ので
どこから叩かれても意味が通るが、エクスプローラだけは pinax が動いている PC の側に
ウィンドウが出る。スマホから押しても、押した本人には何が起きたのか見えない。

### 接続元アドレスで判定してはいけない

最初そうして外した (2026-09-14)。**手元は PC からも Tailscale の口
(`http://100.x.x.x:3838/`) を通して見ている**ので、接続元が pinax 自身のアドレスに
なるとは限らず、PC で見ているのにボタンが出ない。「LAN の中か」でも同じで、
経路の都合を機械が読み切れない。

代わりに 2 つで決める (`src/reveal.ts`):

| 見るところ | 条件 |
|---|---|
| サーバー | `process.platform === 'win32'` — エクスプローラがあるか |
| 画面 (CSS) | 指しか無いと分かった時だけ隠す (`any-pointer: coarse` で、`fine` は無い) |

**画面幅ではなく入力装置で見る。** 横向きのタブレットは幅では PC と区別できない。
CSS のメディアクエリなので端末の向きや外付けマウスの有無にその場で追従し、
JS の状態を持たなくて済む。ただし**書く向き**が要る (次節)。

判断を画面へ預けるので、スマホから叩けば口そのものは通る。LAN / Tailscale の中でしか
開かないサービスで、起きることは「PC にウィンドウが 1 枚開く」だけなので、
ボタンが出ない不便の方が重いという判断。

### 「出す条件」ではなく「隠す条件」を書く

入力装置で見ると決めたあと、`(hover: hover) and (pointer: fine)` で**出す**と書いて
また外した (2026-09-15)。手元の Brave はこの 4 つを全部 false で答える:

```
hover: false / pointer: false / any-hover: false / any-pointer: false
```

`any-` を足しても救えない。**入力装置を答えないブラウザがある**というだけの話で、
「PC だと分かった時だけ出す」と書く限り、判定できない環境は丸ごと「PC ではない」側へ
落ちる。接続元アドレスで外した時と同じ形の失敗 — 機械に読み切れないものを、
読み切れる前提で書いている。

だから逆に書く。**指しか無いとはっきり分かった時だけ隠し、分からなければ出す。**

```css
.pc-only { display: inline-block; }
@media (any-pointer: coarse) { .pc-only { display: none; } }
@media (any-pointer: coarse) and (any-pointer: fine) { .pc-only { display: inline-block; } }
```

スマホは coarse だけが立つので消える。タッチ画面付きのノートは fine も立つので残る。
何も答えないブラウザは 1 行目のまま出る。

サーバーは `available: true` を返し、ボタンは DOM にも出ているのに CSS だけが消す —
**`reason` を持たせた意味が無くなる消え方**で、画面から理由を辿れないのが
一番たちが悪かった。

**パスの検証は落とさない。** `resolveInsideRoot` で蔵書ルートの中に収まっているか必ず
確かめる。DB に入っている値でも信用しない (`/api/files/:id/download` と同じ立場) —
ここを抜かすと `..` を含むフォルダ名 1 つで棚の外を開けるようになる。そちらは実害の話で、
「誰に見せるか」とは別の軸。

## 5.7 ファイルを動かしている間は「答えられない」と言う

スキャンとフォルダの付け替えは `src/lock.ts` で 1 つずつ通す。そのうち
**ファイルを動かす仕事** (`mutates`) が掴んでいる間だけ、
`POST /api/own` は 503 を返して答えない。

黙って答えると事故になる。`files` の同一性は `(root_id, rel_path)` なので、
付け替えの途中の姿を読むと同じファイルが「消えた」と「増えた」の両方に見える。
そこで所持を聞かれると、持っている巻に「持っていない」と答えてしまう —
PowerDowner はそれを信じて落とし直す。

**分からない時に「持っていない」へ倒すのは、入口 (4 章) の話であって、
「今は読めない」とは違う。** 前者は落とし直しで済むが、後者は 503 で聞き直せる。
区別が付くなら区別する。

**スキャン中は断らない。** スキャンは 1 トランザクション (`BEGIN` 〜 `COMMIT`) で
書くので、読む側には前の姿か後の姿しか見えない。途中が見えないのだから断る理由が無く、
3 時間ごとに 50 秒ずつ他のサービスへ 503 を返す方が高くつく。
**排他と「答えない」を同じ線で引かないこと** — 前者は棚の話、後者は契約の話で、
一緒にすると要らない停止時間が生まれる。

## 5.6 並走するシリーズは、機械が決めずに人へ渡す

**書名と著者だけでは、どのシリーズが手元の棚なのか決まらない。**

`title=血界戦線 creator=内藤泰弘` を NDL に投げると 3 つのシリーズが 1 つの答えに混ざる
(2026-09-15 に実測):

```
血界戦線             第1〜10巻   2010-2015    ← 手元にあるのはこれ
血界戦線Back 2 Back   第1〜10巻   2016-2022
血界戦線Beat 3 Peat    第1〜4巻   2023-
```

`byVolume` は巻ごとに 1 本の数直線へ畳むので、**第3巻の椅子を Back 2 Back が取る**。
実際そうなっていた — 中身は無印なのに棚には Back 2 Back の表紙が並び、
`published` の下限も別シリーズの巻で伸びていた。

フォルダ名が `血界戦線` なら無印だろう、と当たりを付けることはできる。**だがやらない。**
`血界戦線 Back 2 Back` というフォルダを作る人はいるし、外したことに気付く手掛かりが
どこにも残らない。要確認 (3 章) と完結 (published.ts) で通してきたのと同じ立場を取る —
**数えて束ねて並べるところまでをやり、決めるのは人。**

```
searchCandidates ──▶ groupCandidates ──▶ 画面に束で並べる ──▶ 人が選ぶ
   (bib/pick.ts)     (bib/candidates.ts)                      │
                                                              ▼
                                            series_pick ──▶ applyPick
                                                 │        (書誌と表紙を貼り直す)
                                                 └──▶ 次からの enrichSeries もこの束だけを見る
```

### 束ね方

鍵は `seriesKeyOf(巻の印と副題を落とした書名)`。ここで 2 つ判断が要る。

**1. 提供元をまたいで 1 つに束ねる。** NDL も楽天も同じシリーズを知っているので、
別々の束にすると人は同じものを 2 回見せられた上にどちらかを選ばされる。しかも
**片方にしか無い巻がある** — 血界戦線の第3巻は NDL の `dcndl:volume` が
`3 (震撃の血槌(ブラッドハンマー))` で、入れ子の括弧を落とせず巻として読めない。
楽天の `血界戦線（3）` でしか拾えない。だから混ぜたまま束ね、
`series_pick` には提供元ではなく**検索の範囲** (`scope`) を残す。

**2. 副題は落とさない。ただし 1 冊しか無い束は親へ畳む。**
副題を常に落とすと `ふしぎ遊戯 : 玄武開伝` が `ふしぎ遊戯` に合流して、同じ壊れ方をする。
落とさないと、NDL が巻ごとの副題を書名へ差し込む癖 (`血界戦線 : 魔封街結社` = 無印の第1巻)
でシリーズが 1 冊ずつに割れる。**巻ごとの副題は 1 冊にしか現れず、別シリーズなら何冊も並ぶ**
ので、そこで切る。

### 貼り直しは、先に落としてから書く

`applyPick` は古い `bib` と (pinned でない) `covers` を**消してから**書く。
上書きだけで済ませると、新しい束に無い巻 (Back 2 Back にしか無い巻) が居残って
`published.max` が嘘の下限のまま伸びる。**嘘の下限が一番まずい** (published.ts の頭)。

ただし**束が見つからなかった時は何も消さない。** 相手が落ちている時に棚の書誌を
道連れにしない。

### 候補の下見はサーバーが中継する

NDL のサムネイルは `Referer: https://ndlsearch.ndl.go.jp/` でないと 403 で弾く。
`Referer` はブラウザが自分で決めるヘッダなので、**画面から直接は名乗れない**
(`http://localhost:3838/` を名乗っても 403。2026-09-15 に実測)。

`/api/bib/thumb` が中継して `data/thumbs/` へ焼く。名前は **URL の SHA-256** —
covers と違って中身のハッシュにはできない (取る前に名前が要る) が、そのぶん
「この URL は取りに行ったか」を DB を引かずに判定できる。一度取った下見は二度と外に聞かない。

行き先は許した書影の置き場だけ (`imageHostAllowed`)。`/api/bib/proxy` と同じで、
任意の URL を取りに行く踏み台にはしない。

**人が画面の前で待っている時だけ間引きを短くする** (300ms)。候補は数枚まとめて出るので、
巡回と同じ 1.2 秒で刻むと一覧が出るまでに十数秒かかる。焼いた後は聞き直さないので
相手への回数は増えない。

## 6. 通知の担当

**PowerDowner と二重に鳴らさない。**

| 出来事 | 出すのは |
|---|---|
| 監視先に新着が出た / 候補が溜まった | DryEyes |
| ジョブの完了・人間待ち・失敗 | PowerDowner |
| **棚に増えた・完結した** | **pinax** |

「ダウンロードが終わった」は PowerDowner が出す。pinax が出すのは棚の変化だけ。
落として棚に入れば両方鳴るが、意味が違う (片方は「落ちた」、片方は「蔵書が増えた」)。

**画面のお知らせと通知は別物。** お知らせ (`events` 表) には必ず残し、通知は出せたら出す。
ntfy が落ちていても新着が消えないようにするため。届かなかったものは印を付けず、次の巡回で試し直す。

## 7. LocalLauncher との関係

```yaml
  - id: pinax
    name: pinax
    description: 漫画の蔵書カタログ（Never burn. Remember Alexandria.）
    command: "start.bat"
    cwd: "C:/Users/seamo/pinax"
    url: "http://100.121.83.66:3838/"
    health_url: "http://127.0.0.1:3838/api/health"
    require_url: true
    icon: "📕"
    profiles: [mowa]
```

守るべき前提 (PowerDowner と同じ):

- **フォアグラウンドで走り続けること。** デーモン化して即 return すると生死を見失われる
- **SIGINT / SIGTERM で片付けること** (`src/index.ts` の `shutdown`)
- **対話的な入力を求めないこと。** 初回も含めて全部 `config.json` で済ませる
- `GET /api/health` は pinax 自体が生きていれば 200。棚の件数とキャッシュの様子も返すので、
  画面を見なくても様子が分かる

### 8.1 受け入れトレイ (Z:) を棚へ入れる

`Z:\90_新悟スペース\JDownLoaderダウンロード` に **3063 個の生ファイルが平置き**されている。

```
100man no Inochi no ue ni ore v15-16s.rar

```

ローマ字・区切りばらばら・拡張子の二重付け。**蔵書と同じ顔で並べてはいけない** ので、
`roots[].kind = "inbox"` として別扱いにする器だけ先に用意してある。

やること:

1. inbox を読んで「これは○○の第15-16巻では?」と**提案**する。
   ローマ字と日本語を繋ぐ手掛かりは 2 つ — 既にある蔵書 485 作品の読み (NDL の
   `dcndl:titleTranscription` が取れる) と、ファイル名の巻数
2. 人が承認したら、`[著者] 作品名/[著者] 作品名 第nn巻.rar` へ整理して NAS へ移す
3. **提案を自動で実行しない。** 3063 件を機械が黙って動かして間違えると、
   どれが元どこにあったか分からなくなる

この段で PowerDowner の `planName` / `fitPath` / `uniqueName` を引き取る。

### 8.2 PowerDowner の台帳を引き取る

今の PowerDowner:

```
DryEyes ──▶ POST /api/jobs ──▶ PowerDowner ──▶ items 表を自分で見て所持判定
```

寄せた後:

```
DryEyes ──▶ POST /api/jobs ──▶ PowerDowner ──▶ POST /api/own (pinax) ──▶ 棚を見て答える
```

**一息にやらないこと。** PowerDowner の README にある通り、台帳は
「間違った行が 1 つあるだけでその巻を永久に落とせなくする」場所。段を踏む:

1. **影運転。** PowerDowner は今まで通り自分の `items` で判定しつつ、pinax にも聞いて
   **答えが食い違った件だけログに出す**。しばらく回して差分の正体を見る
2. 差分が説明できる状態になったら、判定を pinax へ寄せる
3. `items` 表は**消さない**。ダウンロードの履歴としては意味があるし、
   戻せる道を残しておく

食い違いが出る理由は先に分かっている:

- pinax は**ファイルを正**にするので、手で置いたものも消したものも反映される (これが目的)
- 巻数を読めない行の扱い。両方「持っていない」に倒すので落とし直しは起きるが、
  取りこぼしは起きない
- PowerDowner の台帳はユーザー単位だが、pinax の棚は**根 (フォルダ) 単位**。
  ユーザーごとに棚を分けたいなら `roots` を分ける

### 8.3 サジェスト (外部 API の汎用キャッシュプロキシ)

`/api/bib/search` と `/api/bib/proxy` で口は開けてある。これから足すもの:

- **作品名のオートコンプリート。** PowerDowner の「作品として登録する」欄や
  DryEyes の投入設定で作品名を打つと、pinax の蔵書 + 書誌キャッシュから候補が出る。
  表記ゆれ (ローマ字・略称・副題の有無) も吸えるとよい
- 楽天ブックスのアダプタは**済み** (2026-09-14)。次に足すとしたら Google Books だが、
  楽天で 7 割まで来たので急ぎではない
- **書影の候補を人が選ぶ口は済み** (2026-09-15、5.6)。`GET /api/series/:id/cover-search` が
  提供元をまたいでシリーズの束を返すので、作品名のオートコンプリートもここから作れる

### 8.4 合本 (第01-06巻) をどうするか

実測 (2026-09-18、607 作品): **合本は 231 件 / 153 作品 / 799 冊分。**
幅は 2 冊が 113 件、3 冊が 43 件で、半分は 2 冊まとめ。最大 12 冊。

まず**壊れていないもの**をはっきりさせる。欠番と所持の判定は
`catalog.ts` が `volumeFrom..volumeTo` を展開して数えているので、合本でも正しい。
壊れていたのは 2 つだけ:

| | 直したか |
|---|---|
| 表紙が付かない (単巻に限って取りに行っていた) | **済み** (2026-09-18)。496 冊が取りに行ける状態になった |
| 1 冊だけ落とせない。6 冊束で落ちてくる | まだ |

**残っているのは後者だけ**なので、ファイルを割る動機もそれだけ。そして割るのは重い:

- **中の構造が作品ごとにバラバラ。** 6 冊分のフォルダに分かれているのか、
  ページがベタ連番なのか、機械には境界が分からない。当てずっぽうで割ると
  `第03巻` を名乗る別物が棚に載る — 一番やってはいけない壊れ方
- `.rar` は Node だけでは扱えない。「Node.js 24 以上だけあれば動く」が崩れる。
  外部バイナリ (7z / unrar) を `config.json` で受けて、
  **無ければその機能だけ画面に出さない**形にするなら前提は保てる
- 原本を書き換えるのは "Never burn" と正面からぶつかる

やるなら段を踏む:

1. **中を覗いて構造を数える物差し**だけ先に作る (`probe.ts` の圧縮版)。
   231 件のうち何割が機械に割れる形かを見てから決める
2. 割れると分かったものだけ、**原本を消さずに**置く。退避先は棚の外 —
   棚に両方あると重複として数えられる
3. 常駐サーバーから外す。数 GB の再圧縮を 3838 番のプロセスでやると
   `/api/health` が返らなくなり、LocalLauncher に死んだと見なされる
